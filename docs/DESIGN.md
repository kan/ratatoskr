# DESIGN.md — Ratatoskr 設計

## 1. 何を作るのか

個人用のセルフホスト型 RSS リーダー。Cloudflare Workers 上で動作し、PC とスマートフォンから同じ購読状態を共有する。

名前は北欧神話でユグドラシルを往き来し、梢の鷲と根のニーズヘッグの間でメッセージを運ぶリスに由来する。

### 設計の唯一の目標

**livedoor Reader（および Fastladder）の操作感の再現。** 具体的には次の体験を指す。

- キーボードから手を離さずに全購読を消化できる
- キーを押した瞬間に次の記事が表示される（ネットワークを待たない）
- 「この記事を読んだか」を人間に判断させない

機能の網羅性、UI の美しさ、拡張性はいずれもこの目標より下位に置く。

### 明示的に目標としないこと

- 複数ユーザ対応（シングルユーザ専用。この前提が既読モデルを劇的に単純化している）
- 数千フィード規模へのスケール（想定は 50〜150 フィード）
- ソーシャル機能、レコメンド、全文検索
- RSS 以外のソース（Bluesky / AT Protocol を優先、次いで YouTube、Podcast 等）— 将来検討するが MVP の設計制約にはしない

## 2. システム構成

```
                    ┌─────────────────────────────┐
   Cron Trigger ───▶│  Worker (scheduled)         │──▶ 外部フィード
     (5 分毎)        │  crawler                    │    (条件付き GET)
                    └──────────────┬──────────────┘
                                   │
                            ┌──────▼──────┐
                            │     D1      │
                            └──────▲──────┘
                                   │
   ブラウザ ──── Cloudflare ──────▶│  Worker (fetch)             │
   (PC/スマホ)     Access          │  API + Static Assets        │
                                   └─────────────────────────────┘
```

### なぜ Pages ではなく Workers Static Assets か

Workers 単体で静的アセットを配信できるようになっており、API と静的配信を 1 プロジェクトに統合できる。Pages Functions は制約が多く、この構成では利点がない。

### 使わないもの

- **Durable Objects**: 既読状態が単調増加のウォーターマークなので、順序制御を担う中央調停者が不要（§4 参照）
- **Queues**: 想定フィード数では cron 1 回で処理しきれる
- **KV**: D1 で足りる
- **R2**: 画像はオリジンから直接取得し、ブラウザの Cache API に載せる。サーバ側で保持しない
- **Browser Rendering**: 全文取得の本文抽出は `HTMLRewriter` で足りる（§5）。ヘッドレスブラウザを回す必要は無い
- **WebSocket / SSE**: リアルタイム性が要らない。起動時と手動更新時に取れれば十分

## 3. データモデル

スキーマの実体は `migrations/0001_init.sql` を参照。ここでは設計意図を述べる。

### feeds

購読 1 件につき 1 行。フォルダとレートを持つ。`read_seq` が既読ウォーターマーク。

クロール制御のために `etag` / `last_modified` / `content_hash` / `next_fetch_at` / `fetch_interval` / `consecutive_failures` を持つ。

### entries

記事 1 件につき 1 行。`id` は `INTEGER PRIMARY KEY AUTOINCREMENT` で、**クロール時に採番される全体単調増加の値**。この採番順が「読む順序」と「未読判定」の両方を担う。

同一性判定は `guid_hash` で行う。元になる値の優先順位は次の通り。

1. フィードが提供する `guid` / `id`
2. 無ければ記事の `link`
3. それも無ければ `title` + `published` の連結

これを SHA-256 でハッシュ化し、`(feed_id, guid_hash)` に UNIQUE 制約を張って `INSERT OR IGNORE` する。

`body` にはサニタイズ済み HTML のみを格納する。

### entry_states

**ウォーターマークから逸脱する記事だけ**を記録する例外テーブル。具体的には「一度既読になったが手動で未読に戻した記事」。全記事分の行を作らないことで、テーブルサイズを実用上ゼロに保つ。

### pins

ピンは記事の保持期間より長く生き残る必要があるため、`title` と `url` を非正規化して持つ。`entry_id` は参照を残すが、記事削除時は `ON DELETE SET NULL` とし、ピン自体は消さない。

これは LDR の `/api/pin/add` が `subscribe_id` ではなく `title` と `link` を受け取っていた理由でもある。

### 保持期間

既読かつ `stored_at` が 30 日以上前で、ピンされていない記事は削除する。D1 のサイズと未読数集計の速度を保つため。

削除は取得とは別の cron（1 日 1 回）で回す。5 分毎の取得に混ぜると、記事が入るまでの時間にこの掃除がただ積み上がる。既読の判定は未読判定（§4）の裏返しをそのまま使うので、`u` で未読に戻した記事は保持期間を過ぎても残る。1 回の実行で消す件数は区切る（D1 に長時間トランザクションが無く、初回は数万件が対象になり得るため）。消し残しは翌日に持ち越す。

## 4. 既読モデル — 設計の中核

### 仕組み

```
未読       : entries.id > feeds.read_seq
既読化     : UPDATE feeds SET read_seq = MAX(read_seq, ?)
未読数     : SELECT COUNT(*) ... WHERE e.feed_id = f.id AND e.id > f.read_seq
```

フィードを読み終えて次に進んだ時点で、そのフィードの `read_seq` を 1 行 UPDATE するだけで既読化が完了する。記事ごとの既読フラグは存在しない。

### なぜこれが正しいのか

**1. 判断コストがゼロになる。** ユーザは「この記事を読んだか」を意識しない。フィードを送ったら既読、それだけ。LDR の速さの本質は先読みではなくこの割り切りにある。

**2. 複数端末同期が自明になる。** `read_seq` は単調増加なので、衝突解決は `MAX(local, remote)` を取るだけでよい。到着順序を問わず、重複しても壊れない。増加のみのレジスタ（G-Counter に近い CRDT）として振る舞うため、同期のための中央調停者が要らない。これが Durable Objects を使わない理由。

**3. 書き込みが軽い。** 100 記事を既読にしても UPDATE 1 行。

### `published_at` を順序に使わない理由

フィードによっては、公開日時が過去の記事が後から流れてくる。`published_at` で順序を決めると、そうした記事が「既読済みの範囲」に紛れ込んで永久に読まれなくなる。採番 `id` を使えば、いつ届いたものであれ新しい `id` を持つので未読として残る。

### ウォーターマークの送信タイミング

クライアントは「そのフィードのどの記事まで手元に持っていたか」を送る。**送信時点の最新 id ではない。**

ウォーターマークは記事を**表示した時点**でその記事まで進める（離脱時ではない）。離脱を待つとブラウザバックや通信断で取りこぼす。送信自体は outbox でまとめてよい。

LDR / Fastladder は購読ごとに `viewed_on`（時刻）を持つだけで、記事側に既読フラグを持たなかった。この設計はそれを踏襲しつつ、時刻ではなく採番 id を使い、進める単位を「フィードを読み終えたとき」から「記事を表示したとき」に細かくしたものにあたる。読み進めた分が常に残るので、途中で離れても続きから読める。

これは LDR API が `/api/unread` のレスポンスに `last_stored_on` を含め、それを `/api/touch_all` に送り返す設計と同一の考え方である。取得時点までを既読にし、それ以降に届いたものは未読のまま残す。

## 5. クローラ

### 実行

Cron Trigger を 5 分間隔で起動。1 回の実行で処理するフィードは以下で絞る。

```sql
SELECT * FROM feeds
WHERE disabled = 0 AND next_fetch_at <= ?
ORDER BY next_fetch_at
LIMIT 20
```

同時実行数は 4 程度に制限する（`Promise.allSettled` をチャンクに分けて回す）。1 リクエストあたりのサブリクエスト数上限があるため、`LIMIT` を外してはいけない。上限値はプラン依存なので、実装時に現行のドキュメントで確認すること。

### 条件付き GET

`etag` と `last_modified` を保存し、次回リクエストで `If-None-Match` / `If-Modified-Since` として送る。304 が返れば本文を読まずに終了する。相手のサーバへの礼儀であり、こちらの実行時間も激減する。

304 を返さないサーバのために、レスポンス本文の SHA-256 を `content_hash` に保存し、一致したらパースをスキップする。

### 取得間隔の適応制御

- 初期値 1 時間
- 更新が無かった場合、`fetch_interval` を 1.5 倍（上限 6 時間）
- 更新があった場合、1 時間にリセット
- 取得失敗時は `consecutive_failures` を加算し、指数バックオフ（上限 24 時間）
- `consecutive_failures` が 20 を超えたら `disabled = 1` にして UI に警告を出す

### パース

`fast-xml-parser` を使う。RSS 2.0 / Atom / RDF (RSS 1.0) の 3 系統に対応する。`DOMParser` は Workers に存在しない。

日付形式は RFC 822 / RFC 3339 / その他の亜種が混在するため、パースに失敗したら `published_at` は NULL とし、記事自体は取り込む（順序は `id` で決まるので実害がない）。

### サニタイズ

`HTMLRewriter` をホワイトリスト方式のサニタイザとして使う。許可タグ・許可属性以外を除去し、`javascript:` スキームの URL を落とす。ネイティブ実装なので高速で、この用途に適している。

画像は `max-width: 100%` が効くよう、`width` 属性を除去する。

**遅延読み込みの画像は `data-src` 側の実体を採る。** 多くのサイトは `src` に読み込み中の
プレースホルダを置き、本物の URL を `data-src` / `data-original` / `data-lazy-src` に持たせて
スクリプトで差し替える。こちらはスクリプトを動かさないので、`src` をそのまま採ると記事中の
画像が全て同じプレースホルダになる（デイリーポータルZ のスマホ版で実際に踏んだ）。
data 属性側は幅を抑えた版を指していることも多く、拾う方が転送量の面でも良い。

### 要約フィードの全文取得

要約しか配信しないフィードが現実に多い（テクノエッジは `description` が 100 字前後で、本文も画像も記事ページ側にある）。**先読みする画像が無ければ画像の先読みは効かない**ので、全文取得は画像の先読みと同じ「読む前に手元へ落としておく」仕事として扱う。

- **取り込みと同じクロールの中で取りに行く。** 読む時点では既に手元にある形にしたい。「読もうとしたときに取りに行く」形では待ちが出る
- **対象はフィード単位で、決めるのはユーザ**（`feeds.full_text`）。相手のサーバに記事の数だけ取りに行く動作なので、こちらが勝手に始めない。クロール時に要約しか配信していないと見えたら `full_text_suggested` を立て、購読管理画面が勧める
- 取りに行く数は二重に絞る。1 フィード 1 回あたり 10 件、cron 1 回あたり全フィード合わせて 20 件。フィード本体の取得 20 本の上に積み上がるので、サブリクエスト上限に収まる幅に抑える
- 取れた本文は `entries.full_body` に入れ、**`entries.body`（フィードが配信した本文）は残す。** 抽出を仕損じたフィードは設定を切れば元に戻せる（切ったときに `full_body` を消す）。読み出しは `COALESCE(NULLIF(full_body, ''), body)` で 1 つに畳むので、クライアントからはどちらが入っているか見えない
- **取りに行ったが採らなかった記事には印を残す**（`full_body = ''`）。残さないと、セレクタが外れているフィードで未読 10 件を 15 分ごとに取りに行き続けることになる。本文の位置を判定し直したときは印を消して、もう一度試させる
- **本文の位置を決める採点は、素の HTML でも効くようにする。** 手を入れた 2 点はどちらも
  blog.jxck.io（class も id も使わず、`</p>` も省く書き方）で候補が 1 つも出ずに気付いた
  - `</p>` を当てにしない。HTML5 では p の終了タグを省いてよく、`HTMLRewriter` は木を
    組み立てないので暗黙の終了タグはほとんど飛んで来ない。段落は「次の段落が始まった
    とき」「入れ物が開いた / 閉じたとき」に締める
  - class も id も無い入れ物は**タグ名で名指しする**。文書内に 1 つしか無いことは元から
    確かめているので、`article` や `main` のような 1 つしかない入れ物だけが残る
- **段落は `<p>` の中とは限らない。** 虚構新聞は `<article>` 直下に素のテキストを置き、
  改行を `<br>` だけで作る。`<p>` の中だけを数えると候補が 1 つも出ない。全ての文字を
  数え、ブロック要素（`p` / `li` / 見出し / `tr` / `blockquote` 等）で締める
  - **`<br>` だけは、溜まりが段落と呼べる長さに達していなければ締めない。** `<br>` は
    1 つの段落の中の改行にも使われるので、毎回締めると 1 行の短い書き方で加点が全部落ちる
  - **リンクが半分以上を占める塊は段落として数えない。** ナビゲーションや関連記事の一覧は
    `<li>` で組まれているとは限らず、素のリンクが並ぶだけのこともある。数えると下限
    （後述）の分母が膨らみ、本文が切られる。丸ごと捨てるのは、リンク率による比例割引に
    すると `<p>` で書かれた既存のサイトの点数まで全て動くため
- 予算は**取りに行く前に確保する。** クロールはフィードを 4 本並列で回すので、取得を待ってから引くと同じ残りを 4 本が同時に読み、上限の 4 倍まで飛ぶ
- この予算は**記事ページの取得と埋め込みの解決で共有する**。どちらもフィード本体 20 本の上に積み上がるので、合わせて上限に収める

### 埋め込みの扱い

サニタイズはスクリプトと iframe を通さないので、そのままでは**埋め込みが跡形もなく消える**。記事によっては話が繋がらなくなるので、消える代わりに読める形へ置き換える。

- **X のポスト**: サイトが置くのは `<blockquote class="twitter-tweet"><a href="…/status/123"></a></blockquote>` だけで、**本文は HTML に入っていない**（widgets.js がブラウザで取りに行く）。取り込み時に oEmbed（`publish.x.com/oembed`、認証不要）を引いて、本文・投稿者・日時を引用として埋める。返ってきた HTML は必ずサニタイズを通す（不変条件 4）
  - 引き直すのは**中に文字が無い引用だけ**。フィードによっては引用の中にポスト本文がそのまま入っており（痛いニュース）、引き直すと二重になる
  - oEmbed に渡す URL は投稿者と id だけに削る。記事には `?s=20` や `/video/1` の付いた形で貼られ、そのままでは受け付けられない
  - 引けなかった場合（消された・非公開・予算切れ・1 記事あたりの上限超え）は**空の引用のまま残す。** 文言を保存側に焼き付けないことで、後から引き直せる状態を保つ。読み手に何も見えない状態は作らないので、空の引用は表示側で「X のポストを開く」リンクとして描く
  - 埋め込みを引くのは、全文取得を入れていないフィードだけ。入れている場合は記事ページ側の本文が読み出しに使われるので、フィード本文で引いても捨てられる
  - 記事ページからの抽出では、**抽出が確定してから 1 回だけ引く。** 抽出の中で引くと、セレクタを判定し直したときの再抽出でもう一度 X に問い合わせることになる
- **iframe**: 中身は通さないが、**提供元が分かるものに限って**「開く」リンクに差し替える（YouTube / ニコニコ / Vimeo / Spotify 等）。ホストを絞るのは、計測用の隠し iframe までリンクにしないため。差し替えるのはリンクだけで `<p>` では包まない（`<p><iframe></iframe></p>` の形が多く、包むと段落が入れ子になって分断される）
- 引くのは**まだ取り込んでいない記事だけ**。フィードは更新のたびに全件を配り直すので、既知の記事まで対象にすると同じポストを何度も問い合わせることになる。埋め込みを含む記事はごく一部なので、文字列で足切りしてから DB を引く

### 本文の位置をどう決めるか

記事ページのどこが本文かは、**フィードにつき 1 回だけ判定して `feeds.full_text_selector` に覚える。** 同じサイトの記事ページは同じ型で作られているので、記事ごとに聞き直しても答えは変わらない。覚えたセレクタが当たらなくなったら（サイトの作り替え）判定し直す。

**1 ページに複数の記事が並ぶサイトでは、覚えたセレクタだけでは足りない。** 結城浩の日記は月別アーカイブ 1 ページに 1 か月分が並び、記事 URL の `#` 以下がどの記事かを決める。そこで、覚えるのはセレクタ 1 本のままとし、**「当たったもののうち何番目か」を記事ごとにフラグメントから解く。** 採点も切り出しも、アンカーを抱えている最も内側の入れ物の中だけを見る（規則がずれると、A の記事から選んだセレクタを B の記事の位置で切り出す）。絞ったときは id をセレクタに使わない。繰り返し構造の中の id は記事ごとに違うため。

判定は 4 段構えになっている。

1. **候補の採点。** `article` / `main` / `section` / `div` / `td` を候補とし、Readability と同じ考え方で「段落の長さを、その段落を直接抱えている入れ物に満額、その 1 つ上に半額」配る。**2 段までで打ち切るのが肝**で、これが無いとページ全体を包む `div` が必ず 1 位になる（テクノエッジの記事ページは単純なテキスト量ではページ全体を包む `div` が最大で、本文の `article` は 6 位だった）。そのうえでリンク率で割り引く
2. **下限による足切り。** その記事にある文章の 1 割を持たない入れ物は候補にしない。**外枠を本文として掴む事故を止めるため**で、結城浩の日記では候補が著者プロフィールの 1 つだけになり、それが全記事の本文として保存された。全て下回れば候補は 0 件になり、**全文取得を見送って要約のまま残す**
3. **繰り返しによる足切り**（後述）
4. **Workers AI による選択。** 上位 8 件を「セレクタ / 文字数 / リンク率 / 点数 / 書き出し」の一覧にして選ばせる。**渡すのは候補の一覧だけで、HTML そのものではない**（記事ページは 80KB を超え、コンテキストに乗らない）

AI が使えないとき・答えが読めないときは 1 の 1 位に落とす（2 と 3 の足切りを通ったものの中で）。**AI が無いと動かない形にはしない。** 実際、テクノエッジは 1 だけで正解する（AI も同じ候補を選んだ）。

### 繰り返しは本文でない（issue #9）

1 と 2 はどちらもヒューリスティックで、外枠が本文より長い記事では外れる。そこに **「同じフィードの別の記事に、そっくり同じ文章が出てくるなら、それは本文ではない」** という 1 つの規則を足す。本文は記事ごとに違う。これが本文の唯一の定義で、リンク率や文字量と違って外れようがない。

適用するのは 2 か所。

- **選定時**（3）。同じクロールで取れた別々のページを突き合わせ、**2 ページ以上に同じ文章で出てくる候補**を落としてから点数と AI にかける。朝日新聞の記事ページでは著作権表記（183 字・リンク 0）が本文を抜いて 1 位になることがあり、落とさないと点数だけではそれを選ぶ
- **抽出時**。**どの記事も同じ本文になったら**、1 件も採らずにセレクタを疑う。乗り換え先があれば乗り換え、無ければセレクタを捨てて要約のまま残す。**決めたばかりのセレクタなら、そもそも保存しない**（1 ページに複数の記事が並ぶサイトでは突き合わせる別ページが無く、選定時の足切りが効かない）。結城浩の日記は著者プロフィールの入れ物を覚えてしまい、全 15 件の全文が同じ 1329 バイトになっていた。長さでも点数でも表に出ないので、記事どうしを突き合わせるまで気付けない
  - この 2 つ目があるので、**セレクタは決めた時点では保存しない。** 正しいかどうかは、それで抜いてみるまで分からない。決める → 抜いて確かめる → 通ったものだけ保存する、の順にすれば「間違いだったので取り消す」経路が要らなくなる
  - **一部が一致しただけでは疑わない。** フィードは同じ記事を別の URL で 2 度配ることがある（転載、パラメータ違い、別 URL から同じページへのリダイレクト）。それは本当に同じ記事なのでセレクタの誤りではない。外枠を掴んでいるならどの記事も同じ本文になるので、全一致に絞っても取り逃さない

[feedla](https://github.com/tokuhirom/feedla) の `internal/fulltext/boilerplate` が同じ考えで外枠を**削って**から Readability に渡している。こちらは削らず、**本文の入れ物として選ばない**ことだけに使う。この違いは大きい。

- feedla は「リンク率 50% 以上のものだけ削る」という安全弁を要る。連載の定型前書きのような「毎回出る本文の一部」を落とすと、記事が虫食いのまま保存されて後から気付けないため。こちらは削らないので要らない。**実測した外枠はどれもリンクを含まない散文**（朝日新聞の著作権表記、KAI-YOU の編集部紹介）で、その安全弁があると 1 つも落とせなかった
- feedla はフィード単位に署名の出現回数を貯める。こちらは**1 回のクロールで取れたページの中だけ**で突き合わせる。本文の位置をフィードにつき 1 回しか決めないので、決めるその回に手元にある 10 ページで足りる。マイグレーションも永続状態も増えない
- feedla には「出現が半数に満たなければ外枠とみなさない」という条件がある。履歴を貯めて 100 ページ単位で数えるから意味を持つもので、**突き合わせるのが 3 ページまでのこちらでは常に真になる。**「2 ページ以上に出れば外枠」が判定のすべてで、常に真の条件は書かない（読む人に守られていると誤解させる）

指紋は入れ物の中のテキストを順に畳み込んだもの（FNV-1a）。**部分木のテキストを溜め込まない。** 記事ページは 80KB を超え、入れ物ごとに中身を複製すると走査 1 回で何倍にも膨らむ。

繰り返しを数えるのは**別々のページの間だけ**。1 ページに 1 か月分が並ぶ日記型のサイトでは複数の記事が同じ HTML を指すので、そのまま数えると同じページを 3 回見て「どのページにも出る」と誤って判定する。

## 6. クライアント設計

### 起動シーケンス

1. IndexedDB から前回の状態を読んで**即座に描画**（オフラインでも起動する）
2. `GET /api/bootstrap` で全フィードのメタ情報＋未読数＋上位レートのフィードの記事本文を 1 リクエストで取得
3. 描画を更新し、この時点で操作可能にする
4. バックグラウンドで `GET /api/entries` を回して残りの記事本文を取得し、IndexedDB に流し込む
5. 以降の `j` / `k` / `s` / `a` は全てローカル操作。ネットワークを待たない

### 起動時のカーソルは暫定（issue #10）

1 で座らせる位置は**手元の控えだけを頼りにした暫定**で、2 が届いた時点で確かめ直す。

- 手元の既読は、他の端末で読んだ分だけ遅れている（送るのは随時でも、受け取るのは起動と定期同期のときだけ）。遅れた控えのまま座ると、**向こうで読み終えたフィードの既読記事の上にカーソルが乗る。** 未読数だけはサーバの値に直るので、左ペインは 0 なのに記事は出ている、という食い違った状態で始まる
- **座り直すのはユーザがまだ動かしていないときだけ。** 動かしていれば現在位置が着地点と食い違うので、そこで暫定ではなくなる（手で選んだ位置を奪わない）
- **座った時点で `u` の例外は外れる**（「表示したら既読」が唯一の規則）ので、例外だったかどうかはフィードに入る前に控える。控えないと、後で読むために戻した記事が起動のたびに奪われる
- **定期同期では確かめ直さない。** 起動の取得が失敗したときも暫定の印を外すだけにする。読んでいる最中にカーソルが飛ぶ方が困る
- **未読数の申告があるフィードでは、手元の既読記事に落とさない。** 記事が届いていないだけなのを「未読が無い」と読み替えると、結局そのフィードで既読の記事が並ぶ。記事が出せない間は「読み込み中…」と出して、無いと断定しない
- **サーバの未読数は、まだ届いていない `u` の例外を知らない**（送信は outbox 経由で遅れる）。読む対象かどうかの判定でも手元の例外を見る

### なぜ全件先落としが可能か

100 フィード × 未読 20 件でも数千件程度。gzip 後で数 MB に収まる。LDR は「次のフィードだけ」を先読みしていたが、この規模なら全部手元に置ける。結果として体感速度は LDR を上回るはず。

### 背景同期

`GET /api/sync` を 5 分ごとと、タブがフォアグラウンドに戻ったときに叩く（docs/API.md）。

- **タブが隠れていても止めない。** 新着に気付けるようにするのが目的なので（issue #7）、ブラウザがバックグラウンドのタイマを間引くのは構わない
- **戻ったときは 30 秒以内なら叩かない。** 行き来のたびに往復が積み上がる。失敗した回も記録するので、繋がらない間に叩き続けることもない
- **同期が走っている間は次を始めない。** 遅い回線で要求が積み上がらないように
- **同期では左ペインの並びを組み替えない。** サーバの並びは未読数を含むので読み進めるそばから変わり、前方向にしか進まない `s` が未読を飛ばす。並びが変わるのは起動時と、ユーザがレートを変えたときだけ
- **サーバの未読数をそのまま信じない。** `u` で未読に戻した記事はサーバが知らず、保持期間で手元から消した記事はサーバにまだある。当てた後に手元で数え直す

**Access のセッション切れは、繋がらないのとは分けて扱う。** サーバは 401 を返さない。
Access が横取りして、別オリジンのログイン画面へのリダイレクトを返す。既定の
`redirect: 'follow'` だと飛び先が CORS で弾かれ、`TypeError: Failed to fetch` になって
「繋がらない」と見分けが付かない。`redirect: 'manual'` で受けると
`type: 'opaqueredirect'` として手元に返るので、そこで判定する（issue #7）。

- **判定は API クライアント 1 箇所（`web/src/lib/api.ts`）。** 定期同期だけでなく、既読の
  送信も購読の追加も同じリダイレクトに当たる。呼び出し側ごとに書くと、拾い漏れた経路だけが
  黙って失敗し続ける状態に戻る
- **気付いたら定期同期を止める。** ログインし直すまで何を叩いても同じリダイレクトに当たる
- **復帰はナビゲーション要求（＝読み込み直し）でしか通らない。** 画面の振る舞いは
  `docs/UX.md`「ログインの期限切れ」

サーバの状態を手元に当てる手順は bootstrap と共通にしてある。順序に意味がある（未送信分を出し切ってから当てる、当てた直後に差分の起点を取り直す）ので、2 本に分けない。

### 画像の先読みは別扱い

本文 JSON は全件落とせるが、画像は落とせない。数十 MB になり得るため。

そこで **LDRoid のカーソル相対ウィンドウ方式を画像に転用する。**

LDRoid は `PREFETCH_COUNT = 5` として、いま開いたフィードの次から 5 件を直列に先読みしていた（`prefetchStart(position + 1, PREFETCH_COUNT)`）。同じ考え方で、現在のフィードから前後 N 件分に含まれる画像 URL を Cache API に温めておき、ウィンドウから外れたものは破棄する。

- ウィンドウ幅は 3 フィード先まで（設定で変更可能に）
- **同じサイトへは同時に 2 本まで。** 全体の並列度だけで絞ると、1 本のフィードの画像が
  ウィンドウを埋めたときに 4 本とも同じサイトにぶら下がる。記事画像が数 MB あるサイト
  （デイリーポータルZ は原寸 5MB だった）では、それを数十枚ぶん一息に取りに行くことになり、
  相手にとっては短時間の集中アクセスになる。ウィンドウの広さは変えず、1 サイトあたりの
  太さだけを絞る
- **枚数の上限も併せて持つ**（40 枚）。フィード数だけで区切ると、画像の多いフィードが 4 本並んだだけで数百枚を取りに行くことになり、落とし切れないからウィンドウにしたのに元の木阿弥になる。LDRoid の `PREFETCH_COUNT` が件数の上限だったのと同じ
- 並列度は 4。無制限に広げない（相手のサーバに取りに行くため）
- 同一 URL への in-flight リクエストは Map で束ねて重複を防ぐ

**温まるのは 2 箇所ある。** `<img>` が読むのはブラウザの HTTP キャッシュで、Cache API ではない（Cache API は Service Worker がリクエストを横取りして初めて効く）。記事送りを速くしているのは前者で、Cache API への書き込みは §8 の Service Worker がオフラインでも画像を出せるようにするための布石。`fetch` 1 回で両方温まる。

no-cors の応答は opaque（`body` が `null`）なので、本体を読み捨てることも `cancel` することもできない。読まずに放置してもブラウザは最後まで受け取ってキャッシュに載せる。

最後の点は、LDRoid のソースに残っていた TODO（先読み中のフィードをタップすると二重読み込みが発生する）への対応にあたる。

### 先読みは成否を判定できない

**opaque の応答は、成功か失敗かが読めない。** `status` は 0、`body` は `null`、`Timing-Allow-Origin` を返さないサイトでは `PerformanceResourceTiming` のサイズも全部 0 になる。**中身が本当に画像だったかを知る方法は、読ませてみることしかない。**

`no-cors` の cross-origin 応答は、相手が CORS ヘッダを返していても必ず opaque になる。そして記事の画像は必ず外から来る（自分のオリジンが配るのはアプリ本体だけ）。つまり**先読みの側に判定の余地は無い**。

判定を先読みの側に置かない。置くと 2 つ壊れる。

- 先読みは既に `fetch` で 1 回取りに行っているので、確かめるための `<img>` を足すと**相手のサーバへの要求が倍**になる。1 サイト同時 2 本に絞った意味が薄れる
- その確認用の `<img>` 要求を Service Worker が拾い、壊れた応答をランタイムキャッシュ（§8）に焼き付ける。塞いだつもりで裏口が開く

代わりに**記事本文の `<img>` が読めたかどうかを使う。** どうせ読み込むので判定コストがゼロで、しかも「表示に使えるか」という知りたいことそのものを測っている。読めなかったら控えを取り直して読み直す（`web/src/lib/image-repair.ts`）。

- **順序は「取り直してから消す」。** 先に控えを消すと、取り直せなかったとき（圏外・遮断）にオフライン用の写しまで失う。遮断されているだけなら控えの中身は無事なので、消す理由が無い。ネットワーク往復を挟むぶん、Service Worker との競合の窓も狭まる（`image()` はネットワークから取った応答を `waitUntil` で控えるので、削除がその書き込みを追い越すと壊れた応答が焼き直される）。**塞ぎ切ってはいない**が、焼き直されても読み直しがそれを掴んで諦めるだけなので自己終息する
- **取り直しの `fetch` が Service Worker に握られないことに掛かっている。** `routeFor` が cross-origin の非 image destination を素通しし、素の `fetch` の destination は空文字だから成立している。画像ルートを広げると（「cross-origin の GET は全部控える」等）、取り直しに cache-first の同じ壊れた応答が返って修復が黙って死ぬ
- **HTTP キャッシュも `cache: 'reload'` で入れ替える。** Cache API から落としただけだと、読み直しがそちらに残った同じ壊れた応答から返ってくる
- **落とすのは両方の画像キャッシュ。** 先読みの分だけ消しても、Service Worker 側の写し（§8）が残っていれば出続ける
- **取りに行くのは URL につき 1 回、読み直すのは要素につき 1 回。** 前者は 1 つの記事が同じ画像を何度も使う場合のため、後者は「読めない → 読み直す」の輪に入らないための歯止め。取り直しても読めなかった URL は以後諦める。トラッキング防止（Firefox の ETP は Disconnect のリストを使い、はてなの画像 CDN `st-hatena.com` は広告として登録されている）や広告ブロッカーに遮断されている画像は、何度取りに行っても読めない

これが要るのは、**画像の控えが cache-first で取り直されない**ため（§8）。HTTP キャッシュは有効期限で自分から入れ替わるが、Cache API は誰かが消すまで残る。一度でも壊れた応答を掴むと、その端末では二度と出なくなる。

### 先読みが機能する前提条件

**読む順序が事前に確定していること。** LDRoid が購読リストをレート降順にソートしてから先読みしていたのはこのため。Ratatoskr でも同様に、フィードの表示順＝読む順＝先読み順を一致させる。レートはフォルダ分類ではなく「読む順の管理」のための機能である。

### outbox

既読・ピン・レート変更はローカルに即時反映し、送信キューに積む。

- キューは IndexedDB に永続化する（タブを閉じても失われない）
- 送信は `fetch` の `keepalive` オプション付き、`pagehide` 時は `sendBeacon`
- 失敗時は指数バックオフでリトライ
- 全ての操作は冪等。既読は `MAX`、ピンは `INSERT OR REPLACE`
- 送信済みフラグはリクエスト発行**前**に立てる

### カーソルの所有権

「いまどのフィードのどの記事を読んでいるか」は `stores/feeds.ts` が単独で保持する。リーダーコンポーネントは表示専用で、移動要求をイベントで上に投げるだけ。先読みのスケジューリングもストア側が行う。

これは LDRoid で FeedView が `RESULT_NEXT` を返して Main がカーソルを進める構造と同じ責務分割。あちらは Activity の制約から来た苦肉の策だったが、結果として正しい分割になっている。

## 7. 認証

**Cloudflare Access（Zero Trust）を使う。** アプリ側に認証コードを書かず、Worker は `Cf-Access-Jwt-Assertion` ヘッダの JWT を検証するだけでよい。無料枠で足りる。

- 公開鍵は `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs` から取得し、Worker 内でキャッシュする
- `aud` クレームがアプリケーションの AUD タグと一致することを必ず検証する
- ローカル開発時は環境変数でバイパスできるようにする（本番でバイパスが効かないことをテストで担保する）

スマホから毎回パスワードを入力させる体験は「流れるように」から最も遠いので、パスワード認証は選ばない。

## 8. PWA / オフライン

- Service Worker でアプリシェルをプリキャッシュする。**シェルだけでは足りない。**
  初回の訪問では Service Worker がまだ要求を握っていないので、js と css は素通りして
  キャッシュに残らない。その状態で機内モードに入られると、HTML だけが出て中身が動かない。
  インストール時に index.html を読み、そこが参照している `/assets/` まで揃える
  （別立てのプリキャッシュ manifest は持たない。生成を忘れた瞬間に白い画面になる）
- **API はネットワーク優先で、繋がらないときだけ控えを返す。** stale-while-revalidate は
  採らない。クライアントは応答を 1 回しか読まないので、控えを即返すと新着が常に 1 周遅れる。
  起動の速さは IndexedDB からの即描画（§6）で既に確保されていて、ここで稼ぐものが無い
- 控えるのは `/api/bootstrap` だけ。記事の中身は IndexedDB にあるので、同じものを
  2 通りの形で抱えない
- 画像はランタイムキャッシュ（上限を設けて LRU で破棄）。先読み（§6）が温めるキャッシュには
  **書かない**（ウィンドウの出し入れはあちらの持ち物）が、そこから出した画像は自分の側にも
  写す。先読みはウィンドウから外れた画像を捨てるので、写さないと読み終えた記事の画像が
  どこにも残らない
- **画像は cache-first。控えがあれば取りに行かない**（記事送りの速さがここに乗っている）。
  裏を返すと**壊れた応答を掴んでも自分では気付けない**ので、捨てるのは表示側の仕事にする
  （§6「先読みは成否を判定できない」）。写した先も落とされるよう、両方のキャッシュ名を
  `web/src/lib/sw-policy.ts` に置いてページ側と共有する
- ハッシュ付きの資産は、インストール時に index.html が参照しなくなったものを捨てる。
  名前が変わる以上は上書きされず、放っておくとデプロイのたびに積み上がる
- **書き込みには触らない。** 既読・ピンの送信は keepalive / sendBeacon で離脱後も届くことを
  当てにしている経路なので、間に入らない
- outbox が永続化されているので、オフラインで読んでオンライン復帰時に同期できる
- **ホーム画面のアイコンは 3 種類を出し分ける。** 用途ごとに切り抜かれ方が違うので、
  1 枚では足りない
  - `any`（`icon-brand.svg`）… 切り抜かれない場所。フルブリードのまま
  - `maskable`（`icon-maskable.svg`）… Android のアダプティブアイコン。OS が円や
    スクイークルで切り抜くので、**図柄を 80% に縮めて中央に置き**、縁まで地色で埋める。
    フルブリードの図柄をそのまま渡すと、円で切られたときに電波マークが欠ける
  - `monochrome`（`icon-monochrome.svg`）… Android 13 以降のテーマ アイコン。
    ランチャーが壁紙に合わせて塗り直すので、色を持たず形だけを渡す（透明地に不透明の
    図柄）。無いと、他のアプリが単色化される中でこのアプリだけ色付きのまま浮く
  - **正本は SVG で、PNG は `pnpm icons`（`scripts/build-icons.mjs`）から起こす。**
    手で描き直すと「ホーム画面のアイコンだけ古い図柄」という気付きにくい形で残る
- `background_color`（起動時のスプラッシュ）は**暗い側に寄せる**。manifest はテーマを
  持てないので、明暗どちらかに決めるしかない。暗い部屋で白い画面が一瞬出る方が、
  明るい場所で暗い画面が出るより痛い
- `manifest.json` で standalone 表示。テーマ色は `index.html` の meta 1 つで持ち、
  選ばれているテーマに合わせて書き換える（manifest の `theme_color` は 1 色しか
  持てない）。**`prefers-color-scheme` 付きで出し分けない**。テーマは手動でも選べるので、
  システム設定を見る指定のままだと選択と食い違ったときにここだけずれる
- **テーマは `html` の `data-theme` 1 本で決まる。** Tailwind の `dark` バリアントを
  この属性に付け替えてあるので（`web/src/style.css`）、初期値をシステム設定から取るときも
  手で切り替えたときも同じ経路を通る。解決するのは `web/src/lib/theme.ts`
- **保存済みのテーマは最初の描画より前に当てる。** `index.html` のインラインスクリプトが
  `localStorage` を読んで `data-theme` を置く。アプリの読み込みを待つと、システムと
  違う設定にしている人は起動のたびに一瞬だけ逆のテーマを見る。import できない位置なので
  キー名と地色を `lib/` と二重に持つことになるが、食い違いは
  `web/src/lib/theme.test.ts` が突き合わせて検出する
