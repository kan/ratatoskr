**ここが最初の山場。** この時点で既読はまだサーバに反映されない（ローカルのみ）。

実装しながら決めたこと:

- 既読は**記事を表示した時点**でその記事まで進める。フィードの最終記事に到達した時ではない
  （`docs/UX.md`「既読化のタイミング」）。読み進めた分が残り、左ペインの未読数もその場で減る
- `s` / `a` の移動対象は未読のあるフィードのみ。ただし戻る方向は既読のフィードにも入れる
- 全て読み終えたら先頭に戻らず「全て読み終えた」で止まる

## M4: 既読同期

**完了条件: 2 つのブラウザで開き、片方で読んだフィードがもう片方の再読み込み後に既読になっている**

- [x] `POST /api/read`（`MAX` による更新、`batch()` 実行）
- [x] `stores/outbox.ts`（IndexedDB 永続化、指数バックオフ、`keepalive` / `sendBeacon`）
- [x] 表示した記事までの既読化発行（送信済みフラグは発行前に立てる）
- [x] `GET /api/sync` のクライアント側マージ（`Math.max` で受ける）
- [x] `POST /api/entries/:id/unread` と `u` キー
- [x] **ウォーターマークのユニットテスト**（巻き戻らないこと、新着が既読にならないこと、重複送信で壊れないこと）

実装しながら決めたこと:

- **`u` で未読に戻した記事は他の端末に伝わらない。** サーバの `entry_states` には入るが、
  `GET /api/bootstrap` も `GET /api/sync` も例外を返さないので、別の端末はその記事を
  未読と判定できない。既読ウォーターマークの同期は完全に動く。返し方を決めるのは
  変更追跡（`feeds` の更新時刻、削除済みピン）と同じ話なので、`since` を有効化する
  ときに一緒に設計する
- 既読は**表示した記事の id** を 2 秒ごとにまとめて送る。離脱時は `sendBeacon`。
  未読戻しは URL とメソッドが記事ごとに違って `sendBeacon` に載らないので、
  `keepalive` 付きの `fetch` で投げる
- 未読に戻した記事を**もう一度表示しに行ったら例外は外れる**。「表示したら既読」を
  唯一の規則にしておかないと、一度 `u` を押した記事が読んでも消えなくなる。
  ただしリストの差し替え（背景取得）で反応してはいけないので、既読化と例外解除は
  カーソルが別の記事に動いたときだけ走らせる
- IndexedDB のスキーマは 2 に上げた。outbox と未読例外は**サーバから取り直せない
  唯一のデータ**なので、以降のスキーマ変更でもキャッシュ（feeds / entries / meta）と
  違って捨てない

## M5: 購読管理

**完了条件: UI からフィードを追加・削除でき、OPML で往復できる**

- [x] `POST /api/feeds`（フィード自動検出、同期的な初回クロール、複数候補の提示）
- [x] `PATCH /api/feeds/:id` / `DELETE /api/feeds/:id`
- [x] `POST /api/feeds/:id/fetch` と `r` キー
- [x] レート（`1`–`5` キー、左ペインの即時再ソート、先読みウィンドウの再計算は M7）
- [x] フォルダ
- [x] `GET /api/opml` / `POST /api/opml`
- [x] 購読管理画面（ここだけは普通のフォーム UI でよい）

実装しながら決めたこと:

- **フォルダは左ペインのグループ化には使わない。** 左ペインの並びはレート順が正
  （`docs/UX.md` の画面構成）。フォルダは購読管理画面での分類と OPML の入れ子だけに使う
- **追加と削除は outbox を通さない。** フィードの検出も初回クロールもサーバでしかできず、
  結果（候補の提示、取れた記事）をその場で見せる必要がある。読んでいる最中に押される
  レート変更だけが outbox 経由（不変条件 3）
- **購読管理の入口にキーは割り当てない。** `docs/UX.md` のキー表を勝手に増やさないため、
  左ペインのボタンから開く
- **フィード名は `<link title>` ではなくフィード自身の名乗りを使う。** `title="Atom"` の
  ような総称であることが多く、そのまま採用すると購読名が「Atom」になる
- **自動検出は `<link rel="alternate">` だけを見る。** `/feed` `/rss.xml` のような定番パスの
  推測はしない。フィードを広告していないサイト（朝日新聞など）は URL を直接貼る
- OPML の取り込みは 1 回 500 件まで。初回クロールはせず、記事が入るのは次の定期取得
- `s` はレート変更で並びが変わっても**前方向にしか進まない**（M3 の決定のまま）。
  レートを下げて上に移った未読フィードには `a` で戻る

## M6: ピン

**完了条件: `p` でピンし、`z` で一覧を開き、`o` で全てタブに開ける**

- [x] `POST /api/pins` / `DELETE /api/pins/:id`
- [x] `p` / `z` / `o` キー
- [x] `PinList.vue`（オーバーレイ）
- [x] 記事削除後もピンが残ることの確認

実装しながら決めたこと:

- **手元でのピンの同一性は id ではなく url。** 送信が通るまでの仮 id は起動をまたぐと
  採番が巻き戻り、別のピンを巻き添えに消す。url ならサーバの UNIQUE と同じ単位で、
  採番に依存しない
- **ピンだけは outbox の送信結果を使う。** 外すには id が要り、id を知る手段が
  応答しか無いため。応答で仮 id を差し替える。送信中に外された場合は、id が判ってから
  改めて外す（取り消したつもりでサーバに残ると、次の bootstrap で復活する）
- **`o` は開けた分だけピンから外す。** ブラウザは 1 回の操作で開けるタブ数を絞ることが
  あり、全部消してからブロックに気付くと控えが失われる。`window.open` は `noopener` を
  付けると**ブロックされていなくても戻り値が null になる**ので、判定したいこの経路では
  付けずに開き、直後に `opener` を切る
- ピンした記事の目印は左ペインと記事の見出しに出す。見出しの目印はタイトルの外に置く
  （見出しの文言そのものを変えないため）

## M7: 画像の先読みと全文取得

**完了条件: フィードを送った直後に、本文と画像が既に表示されている**

- [x] `lib/prefetch.ts` — カーソル相対ウィンドウ（3 フィード先、並列度 4）
- [x] in-flight リクエストの束ね（同一 URL の重複排除）
- [x] ウィンドウ外の破棄
- [x] Cache API への書き込み

### あわせて検討する: 要約フィードの全文取得

**先読みする画像が無ければ、画像の先読みは効かない。** M3 で実際に購読して分かったとおり、
要約しか配信しないフィードが現実に多い（テクノエッジは `description` 100 字ほどで、画像も
本文も記事ページ側にある）。画像の先読みと全文取得は同じ「読む前に手元へ落としておく」
仕事なので、切り離さずにここで一緒に設計する。

決めたこと:

- [x] 全文取得の対象をどう判定するか → **フィード単位の設定（`feeds.full_text`）。既定は切**。
      クロール時に要約しか配信していないと見えたら購読管理画面で勧める（`full_text_suggested`）
- [x] 取得と本文抽出をどこでやるか → **取り込みと同じクロールの中でサーバ側**。
      `HTMLRewriter` によるサニタイズを取り込み時と共有できる
- [x] 本文らしい部分の取り出し方 → **候補の採点（Readability 相当）+ Workers AI による選択**。
      判定はフィードにつき 1 回だけで、結果をセレクタとして覚える
- [x] 相手サーバへの礼儀 → 1 フィード 1 回 10 件・cron 1 回 20 件の二重の上限、フィード内は並列度 2
- [x] 保存量 → `entries.full_body` に別で持ち、`entries.body` は残す。読み出しは `COALESCE`

M3 の時点で「フィードが配信している本文」は全件手元にある。ここで足すのは、
フィードに載っていない部分（画像の実体と、要約フィードの本文）。

実装しながら決めたこと:

- **`<img>` は Cache API を読まない。** Cache API は Service Worker がリクエストを横取りして
  初めて効くので、M7 の時点で記事送りを速くしているのはブラウザの HTTP キャッシュの方。
  Cache API への書き込みは M8 でオフラインでも画像を出すための布石で、`fetch` 1 回で
  両方温まる。no-cors の応答は opaque（`body` が `null`）なので、本体を読み捨てることも
  `cancel` することもできない。放置してもブラウザは最後まで受け取ってキャッシュに載せる
- **先読みウィンドウはフィード数だけでなく枚数でも区切る**（40 枚）。画像の多いフィードが
  4 本並ぶと数百枚になり、落とし切れないからウィンドウにしたのに元の木阿弥になる
- **本文の位置は 2 段までしか点を配らない。** 段落の長さをその入れ物と 1 つ上にだけ配る。
  3 段以上に配るとページ全体を包む div が必ず 1 位になる（テクノエッジの記事ページは
  単純なテキスト量ではページ全体を包む div が最大で、本文の article は 6 位だった）
- **AI が無くても動く形にした。** 渡すのは候補の一覧（数百トークン）だけで HTML は渡さない。
  答えが読めなければ点数の 1 位に落ちる。テクノエッジは点数だけで正解し、AI も同じ候補を
  選んだ。Workers AI の応答は `{ response }` と OpenAI 互換の
  `{ choices[].message.content }` の 2 通りがあり、後者を見落とすと黙って点数に落ち続ける
- **フィードの本文より短い抽出は採らない。** 抽出が外れると注釈やパンくずだけを掴む形で
  失敗する。書き込むと全文取得を入れたせいで読めるものが減る
- **`POST /api/feeds/:id/fetch` は新着だけでなく、本文が差し替わった記事も返す。**
  既にクライアントが持っている記事なので `sinceId` の差分に出てこず、返さないと
  設定を入れた直後に手持ちの未読が要約のまま残る
- Workers AI のバインディングは必ずリモートに繋ぎに行くので、テストでは
  `remoteBindings: false` で無効にする（有効なままだと認証が要り、プロセスが終了しない）
- **埋め込みは落とすだけでは済まない。** サニタイズはスクリプトと iframe を通さないので、
  X のポストと動画が跡形もなく消えて記事の意味が通らなくなる。X はポスト本文が
  そもそも記事ページに無い（widgets.js がブラウザで取りに行く）ので、取り込み時に
  oEmbed から引いて埋める。iframe は提供元が分かるものだけ「開く」リンクに差し替える
- **本文の見た目にも手を入れた。** 見出しのサイズ差・表の罫線・行長の制限・埋め込み
  ブロックの枠。全文取得で長い記事が入るようになると、フラットな装飾では読み進めづらい
