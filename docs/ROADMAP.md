## M4: 既読同期

**完了条件: 2 つのブラウザで開き、片方で読んだフィードがもう片方の再読み込み後に既読になっている**

- [x] `POST /api/read`（`MAX` による更新、`batch()` 実行）
- [x] `stores/outbox.ts`（IndexedDB 永続化、指数バックオフ、`keepalive` / `sendBeacon`）
- [x] 表示した記事までの既読化発行（送信済みフラグは発行前に立てる）
- [x] `GET /api/sync` のクライアント側マージ（`Math.max` で受ける）
- [x] `POST /api/entries/:id/unread` と `u` キー
- [x] **ウォーターマークのユニットテスト**（巻き戻らないこと、新着が既読にならないこと、重複送信で壊れないこと）

実装しながら決めたこと:

- **`u` で未読に戻した記事は他の端末に伝わらない。** サーバの `entry_states` には入るが、
  `GET /api/bootstrap` も `GET /api/sync` も例外を返さないので、別の端末はその記事を
  未読と判定できない。既読ウォーターマークの同期は完全に動く。返し方を決めるのは
  変更追跡（`feeds` の更新時刻、削除済みピン）と同じ話なので、`since` を有効化する
  ときに一緒に設計する
- 既読は**表示した記事の id** を 2 秒ごとにまとめて送る。離脱時は `sendBeacon`。
  未読戻しは URL とメソッドが記事ごとに違って `sendBeacon` に載らないので、
  `keepalive` 付きの `fetch` で投げる
- 未読に戻した記事を**もう一度表示しに行ったら例外は外れる**。「表示したら既読」を
  唯一の規則にしておかないと、一度 `u` を押した記事が読んでも消えなくなる。
  ただしリストの差し替え（背景取得）で反応してはいけないので、既読化と例外解除は
  カーソルが別の記事に動いたときだけ走らせる
- IndexedDB のスキーマは 2 に上げた。outbox と未読例外は**サーバから取り直せない
  唯一のデータ**なので、以降のスキーマ変更でもキャッシュ（feeds / entries / meta）と
  違って捨てない

## M5: 購読管理

**完了条件: UI からフィードを追加・削除でき、OPML で往復できる**

- [x] `POST /api/feeds`（フィード自動検出、同期的な初回クロール、複数候補の提示）
- [x] `PATCH /api/feeds/:id` / `DELETE /api/feeds/:id`
- [x] `POST /api/feeds/:id/fetch` と `r` キー
- [x] レート（`1`–`5` キー、左ペインの即時再ソート、先読みウィンドウの再計算は M7）
- [x] フォルダ
- [x] `GET /api/opml` / `POST /api/opml`
- [x] 購読管理画面（ここだけは普通のフォーム UI でよい）

実装しながら決めたこと:

- **フォルダは左ペインのグループ化には使わない。** 左ペインの並びはレート順が正
  （`docs/UX.md` の画面構成）。フォルダは購読管理画面での分類と OPML の入れ子に使う
  - 後から左ペインでの**絞り込み**を足した（issue #3）。**グループ化ではない**ので
    この線引きは変わらない。並びはレート順のままで、フォルダは読む対象を狭めるだけ
    （`docs/UX.md` の「フォルダ」）
- **追加と削除は outbox を通さない。** フィードの検出も初回クロールもサーバでしかできず、
  結果（候補の提示、取れた記事）をその場で見せる必要がある。読んでいる最中に押される
  レート変更だけが outbox 経由（不変条件 3）
- **購読管理の入口と購読の解除にはキーを割り当てる**（`m` / `Shift+X`、issue #8）。
  当初は「キー表を増やさない」として左ペインのボタンだけにしていたが、読んでいる最中に
  「これはもう要らない」と思ったその場で押せることの方が効く。ボタンは残す
  （キー表に載せる基準は `docs/UX.md`）
- **フィード名は `<link title>` ではなくフィード自身の名乗りを使う。** `title="Atom"` の
  ような総称であることが多く、そのまま採用すると購読名が「Atom」になる
- **自動検出はページに書いてあるものだけを見る。** `<link rel="alternate">` が本命で、
  それが 1 つも無いときに限り `<a href>` に落ちる。虚構新聞のように、自動検出用のタグを
  出さず人間向けのリンク（`<a href="index.xml">RSSフィード</a>`）だけを置くサイトがある。
  **`/feed` `/rss.xml` のような定番パスの推測はしない。** 貼られた URL で見つからない
  ときは、そのパスを 1 段ずつ 3 段まで遡って同じことを試す（記事詳細ページにフィードの
  在処が書かれていないサイトがある。note がこれ）。推測するのは「上の階層」までで、
  フィードのファイル名は推測しない。遡るのは**取れたが候補が 0 件だったとき**だけで、
  404 や接続の失敗はそのまま理由を返す。`<a>` を見るのは同一サイト内に限り、
  フィードらしいパスだけを候補にする。それでも見つからないサイトは URL を直接貼る
- OPML の取り込みは 1 回 500 件まで。初回クロールはせず、記事が入るのは次の定期取得
- `s` はレート変更で並びが変わっても**前方向にしか進まない**（M3 の決定のまま）。
  レートを下げて上に移った未読フィードには `a` で戻る

## M6: ピン

**完了条件: `p` でピンし、`z` で一覧を開き、`o` で全てタブに開ける**

- [x] `POST /api/pins` / `DELETE /api/pins/:id`
- [x] `p` / `z` / `o` キー
- [x] `PinList.vue`（オーバーレイ）
- [x] 記事削除後もピンが残ることの確認

実装しながら決めたこと:

- **手元でのピンの同一性は id ではなく url。** 送信が通るまでの仮 id は起動をまたぐと
  採番が巻き戻り、別のピンを巻き添えに消す。url ならサーバの UNIQUE と同じ単位で、
  採番に依存しない
- **ピンだけは outbox の送信結果を使う。** 外すには id が要り、id を知る手段が
  応答しか無いため。応答で仮 id を差し替える。送信中に外された場合は、id が判ってから
  改めて外す（取り消したつもりでサーバに残ると、次の bootstrap で復活する）
- **見出しの無い記事も断らない**（issue #11）。タイトルを配らないフィードの記事を
  「`title` は必須」で 400 にしていたが、**outbox は 4xx を「送り直しても通らない」として
  黙って捨てる**ので、ピンは画面に出たままリロードで消えていた。サーバに拒まれる値を
  クライアントが正当に持てる形にしてはいけない。空で受けたうえで、記事がまだあるうちに
  M7 と同じ規則（本文の書き出し）で見出しを作って控える——**ピンは記事より長生きする**
  ので、URL しか残らないと一覧を見ても何をピンしたのか分からない
- **`o` は開けた分だけピンから外す。** ブラウザは 1 回の操作で開けるタブ数を絞ることが
  あり、全部消してからブロックに気付くと控えが失われる。`window.open` は `noopener` を
  付けると**ブロックされていなくても戻り値が null になる**ので、判定したいこの経路では
  付けずに開き、直後に `opener` を切る
- ピンした記事の目印は左ペインと記事の見出しに出す。見出しの目印はタイトルの外に置く
  （見出しの文言そのものを変えないため）

### あわせて検討する: 要約フィードの全文取得

**先読みする画像が無ければ、画像の先読みは効かない。** M3 で実際に購読して分かったとおり、
要約しか配信しないフィードが現実に多い（テクノエッジは `description` 100 字ほどで、画像も
本文も記事ページ側にある）。画像の先読みと全文取得は同じ「読む前に手元へ落としておく」
仕事なので、切り離さずにここで一緒に設計する。

決めたこと:

- [x] 全文取得の対象をどう判定するか → **フィード単位の設定（`feeds.full_text`）。既定は切**。
      クロール時に要約しか配信していないと見えたら購読管理画面で勧める（`full_text_suggested`）
- [x] 取得と本文抽出をどこでやるか → **取り込みと同じクロールの中でサーバ側**。
      `HTMLRewriter` によるサニタイズを取り込み時と共有できる
- [x] 本文らしい部分の取り出し方 → **候補の採点（Readability 相当）+ Workers AI による選択**。
      判定はフィードにつき 1 回だけで、結果をセレクタとして覚える
- [x] 相手サーバへの礼儀 → 1 フィード 1 回 10 件・cron 1 回 20 件の二重の上限、フィード内は並列度 2
- [x] 保存量 → `entries.full_body` に別で持ち、`entries.body` は残す。読み出しは `COALESCE`

M3 の時点で「フィードが配信している本文」は全件手元にある。ここで足すのは、
フィードに載っていない部分（画像の実体と、要約フィードの本文）。

実装しながら決めたこと:

- **`<img>` は Cache API を読まない。** Cache API は Service Worker がリクエストを横取りして
  初めて効くので、M7 の時点で記事送りを速くしているのはブラウザの HTTP キャッシュの方。
  Cache API への書き込みは M8 でオフラインでも画像を出すための布石で、`fetch` 1 回で
  両方温まる。no-cors の応答は opaque（`body` が `null`）なので、本体を読み捨てることも
  `cancel` することもできない。放置してもブラウザは最後まで受け取ってキャッシュに載せる
- **先読みウィンドウはフィード数だけでなく枚数でも区切る**（40 枚）。画像の多いフィードが
  4 本並ぶと数百枚になり、落とし切れないからウィンドウにしたのに元の木阿弥になる
- **本文の位置は 2 段までしか点を配らない。** 段落の長さをその入れ物と 1 つ上にだけ配る。
  3 段以上に配るとページ全体を包む div が必ず 1 位になる（テクノエッジの記事ページは
  単純なテキスト量ではページ全体を包む div が最大で、本文の article は 6 位だった）
- **AI が無くても動く形にした。** 渡すのは候補の一覧（数百トークン）だけで HTML は渡さない。
  答えが読めなければ点数の 1 位に落ちる。テクノエッジは点数だけで正解し、AI も同じ候補を
  選んだ。Workers AI の応答は `{ response }` と OpenAI 互換の
  `{ choices[].message.content }` の 2 通りがあり、後者を見落とすと黙って点数に落ち続ける
- **フィードの本文より短い抽出は採らない。** 抽出が外れると注釈やパンくずだけを掴む形で
  失敗する。書き込むと全文取得を入れたせいで読めるものが減る
- **`POST /api/feeds/:id/fetch` は新着だけでなく、本文が差し替わった記事も返す。**
  既にクライアントが持っている記事なので `sinceId` の差分に出てこず、返さないと
  設定を入れた直後に手持ちの未読が要約のまま残る
- Workers AI のバインディングは必ずリモートに繋ぎに行くので、テストでは
  `remoteBindings: false` で無効にする（有効なままだと認証が要り、プロセスが終了しない）
- **埋め込みは落とすだけでは済まない。** サニタイズはスクリプトと iframe を通さないので、
  X のポストと動画が跡形もなく消えて記事の意味が通らなくなる。X はポスト本文が
  そもそも記事ページに無い（widgets.js がブラウザで取りに行く）ので、取り込み時に
  oEmbed から引いて埋める。iframe は提供元が分かるものだけ「開く」リンクに差し替える
- **本文の見た目にも手を入れた。** 見出しのサイズ差・表の罫線・行長の制限・埋め込み
  ブロックの枠。全文取得で長い記事が入るようになると、フラットな装飾では読み進めづらい
- **「同じフィードの別の記事に同じ文章が出るなら本文ではない」を足した**（issue #9）。
  点数と占有率の下限はどちらもヒューリスティックで、外枠が本文より長い記事では外れる。
  本文が記事ごとに違うことだけは外れようがないので、選定時に「複数ページに同じ文章で
  出る候補」を落とし、抽出時に「別の記事と同じ本文になったもの」を採らない
  （`docs/DESIGN.md` の「繰り返しは本文でない」）。参考にした feedla は外枠を**削る**ので
  「リンク率 50% 以上」の安全弁が要るが、こちらは**選ばない**だけなので要らない。
  実測した外枠（朝日新聞の著作権表記・KAI-YOU の編集部紹介）はどれもリンクを含まない
  散文で、その安全弁があると 1 つも落とせなかった
- **タイトルを配らないフィードでは、本文の書き出しを見出しにする。** Bluesky の
  プロフィール RSS には item の title が無く、左ペインが「(無題)」で埋まる
  （`docs/DESIGN.md` の「タイトルを配らないフィード」）。**HTMLRewriter の `*` は
  要素に包まれていない直下のテキストに当たらない**ので、素のテキストを本文にする
  フィードでは `onDocument` で拾う必要がある（`*` で書いて見出しが常に空になった）
- **Bluesky は記事ページを見ずに API から組み立てる。** bsky.app の投稿ページは SPA で
  本文が HTML に入っておらず、走査しても候補が出ない。RSS にはテキストが最初から
  入っているので、API から採るのは画像・リンクカード・引用・リンクの facet と改行
  （`docs/DESIGN.md` の「Bluesky は記事ページを見ない」）。**画像が `<img>` で本文に
  入って初めて画像の先読みが効く**のが理由で、10 件を 1 リクエストで取れるぶん
  相手のサーバへの負担も減る。取り込みは今までどおり RSS なので、
  「Bluesky をソースとして扱う」（将来検討）には踏み込んでいない
- **終了タグの無い要素に `onEndTag` を登録すると、走査が丸ごと落ちる。** HTMLRewriter が
  「No end tag」を投げる。空要素（`<hr>`）だけでなく、**SVG / MathML の中では HTML と違って
  自己終了タグが有効**なので `<svg class="i"/>` や `<svg><a href="#"/></svg>` でも再現する。
  例外は `Promise.allSettled` に拾われるので、そのフィードだけ静かに全文が埋まらなくなる
  （実際の記事ページ 44 本に当てて `<hr>` の側を見つけた）。握り潰すだけでは足りない。
  「開いた」印を下ろす当てが無いまま立てると、そこから後ろが全部その要素の中の扱いになる
  ので、**入るより先に出口を押さえる**（`src/crawler/rewriter.ts` の `elementScope`）

## M8: スマホ UI / PWA

- [x] オフライン時の outbox 動作確認

実装しながら決めたこと:

- **ボトムバーもスワイプも `j` / `k` と同じ経路を通す。** 境界でフィードを跨ぐ判断は
  カーソルの所有者（`stores/feeds.ts`）が既に持っているので、押す側は「次へ」を
  投げるだけでよい。別経路にすると、キーとボタンで境界の扱いが食い違う
- 広い / 狭いの境目は Tailwind の `md`（768px）に揃えた。CSS の `md:` と JS の
  `matchMedia` で違う値を見ると、左ペインが出ているのにボトムバーも出る形が生まれる
- **フィード一覧の引き出しは、閉じている間は組み立てない。** 見えていない一覧の
  再描画に記事送りが付き合わされないように
- **触る画面には hover が無い。** 左ペインの購読解除は普段は文字色を透明にしてあるので、
  狭い画面では最初から出す（M5 の「行に触れたときに出す」は指のある画面では成立しない）
- 購読管理の表は狭い画面で横に流す。列幅を決めたまま詰めると、タイトルが 1 文字ずつ
  縦に折り返って読めなくなる（本文の表と同じ扱い）
- スワイプは**横スクロールする入れ物（`pre` / `table`）の中から始まった指を捨てる。**
  表やコード片を横に送るつもりで記事が飛ぶと、読み返す手立てが無くなる
- 下端からの引きは**下端に着いた時点を起点に測る。** 指を置いた場所から測ると、本文の
  途中から下端まで一息に送る動き（普通の読み方）がそのまま記事送りになる。
  逆に、既に下端にいるなら指を置いた場所が起点（最初の `touchmove` を待つと、
  勢いよく引いた分がまるごと捨てられる）
- 引きの深さは左右スワイプより深くしてある（90px 対 60px）。読み終わりの数行を送る指と
  地続きの動きなので、同じ深さだと「最後の 1 画面を送ったつもり」で飛ぶ
- **「離すと次の記事へ」は本文の中に置かない。** 出した分だけ本文が伸びて「もう下端では
  ない」状態になり、出したり消したりを繰り返す。重ねて出せば高さに響かない
- **API はネットワーク優先にした**（`docs/DESIGN.md` §8 を実装に合わせて直した）。
  stale-while-revalidate だと、クライアントは応答を 1 回しか読まないので新着が常に
  1 周遅れる。起動の速さは IndexedDB からの即描画で既に確保されている
- **アプリシェルだけをプリキャッシュしても、オフラインでは白い画面になる。** 初回訪問の
  時点では Service Worker がまだ要求を握っておらず、js と css がキャッシュに残らない。
  インストール時に index.html を読んで `/assets/` を起こす形にした（実際に踏んで直した）
- Cache API の `put` は同じ key の記録を置き換えたうえで**末尾に積み直す**（実測）。
  参照したものを入れ直すだけで `keys()` が「最後に使った順」になり、先頭から捨てれば LRU
- Service Worker は本番ビルドにだけ登録する。開発中は Vite がモジュールを都度配るので、
  間にキャッシュを挟むと何が古いのか分からなくなる。手元での確認は
  `pnpm build && pnpm -C web preview`
- オフラインで起動すると `/api/entries` は失敗するので、「サーバに繋がらない」の帯は
  出たままになる。控えているのは bootstrap だけなので、これは正しい状態
- **控える仕事は `event.waitUntil` に預ける。** 応答を返した時点で Service Worker は
  止められうるので、投げっぱなしの書き込みは落とされる。画像は出てしまうので、
  気付けない形で控えだけが虫食いになる
- **置けなかったときこそ古い分を捨てる。** 書き込みが失敗する主因は容量超過で、そこで
  戻ると次の書き込みも同じ理由で失敗し、満杯のまま二度と入れ替わらないキャッシュになる
- ナビゲーションでも**拡張子の付いたパスはシェル扱いにしない。** `/manifest.json` を
  アドレス欄から開くのも同じ形で届くので、シェルとして控えると次のオフライン起動で
  その中身が出る（`/api/opml` と同じ罠を、API の側だけ塞いでいた）
- **`/api/` の判定はナビゲーションより先。** `<a href="/api/opml">` はナビゲーション要求で
  届く（`wrangler.jsonc` の `run_worker_first` と同じ話）ので、順序を逆にすると書き出した
  OPML がアプリシェルとして控えられ、次のオフライン起動で画面の代わりに OPML が出る。
  レビューで指摘されて実際に再現した
- **先読みの控えから出した画像は、Service Worker 側にも写す。** 先読みはウィンドウから
  外れた画像を捨てるので、写さないと「読み終えた記事の画像」がどこにも残らない
  （`k` で戻った先が空になる）。写す先の上限が LRU で効く
- 同一オリジンの画像（アプリのアイコン）は記事の画像と別扱いにする。混ぜると記事の
  画像に押し出されるうえ、置き換わっても取り直されない
- ハッシュ付きの資産は、インストール時に **いま index.html が参照していないものを捨てる。**
  名前が変わる以上は上書きされないので、放っておくとデプロイのたびに 1 組ずつ積み上がる
- **ヘルプに閉じるボタンを足した。** 初回起動で自動的に開く画面（`docs/UX.md`）なのに、
  閉じる手立てが Esc と背景の細い余白しか無く、スマホの初回起動がそこで詰まっていた
- **Service Worker は E2E を別プロジェクトに分けた**（`playwright.config.ts` の `pwa`）。
  開発サーバでは登録されないので、組み上げた `dist` を `vite preview` で配って当てる。
  上の 2 つは、この形にして初めて壊れに気付ける（実際、直す前は両方とも落ちる）

## M9: 運用

**完了条件: 本番に上げて、放っておいても DB が太らず、壊れたフィードに気付ける**

- [x] 保持期間による記事削除（cron 内で 1 日 1 回）
- [x] `consecutive_failures` 超過フィードの UI 警告
- [x] デプロイ手順の README 化
- [x] D1 のバックアップ方針

実装しながら決めたこと:

- **掃除は取得とは別の cron に分けた**（`*/5 * * * *` と `23 17 * * *`）。5 分毎の実行に混ぜると、
  記事が入るまでの時間にこの掃除がただ積み上がる。どちらの仕事かは `event.cron` で振り分ける
- **cron 文字列が `wrangler.jsonc` と食い違うと、掃除は一度も走らない。** しかも何も起きないだけなので
  動かしていて気付けない。`src/index.test.ts` で設定ファイルを読んで突き合わせている
- 消してよいのは「既読・未ピン・保持期間を過ぎた」が揃ったものだけ。既読の判定は未読判定
  （`src/db/unread.ts`）の裏返しをそのまま使う。独自の条件を書くと、`u` で未読に戻した記事が
  画面には出ているのに実体が無い状態になる
- **1 回の実行で消す件数を区切る**（500 件ずつ、1 回 10,000 件まで）。D1 には長時間トランザクションが
  無く、初回は数万件が対象になり得る。消し残しても読む分には困らないので、翌日に持ち越す
- 連続失敗のしきい値（20）は `shared/types.ts` に置いて、取得を止める側（サーバ）と止まったことを
  知らせる側（画面）で同じ値を見る。片方だけ変えると、止まっているのに警告が出ない状態が生まれる
- 警告は左ペインの頭に出し、押すとそのまま購読管理へ入る。**読む場所には出さない**（記事が増えなく
  なるだけの話に、読んでいる最中の画面を使わない）。手で「停止」したフィードを巻き込まないよう、
  判定はサーバの `shouldDisable` と同じ式（`disabled` かつ連続失敗がしきい値超え）にする
- バックアップは 3 段（Time Travel / SQL ダンプ / OPML）。**失うと取り返しがつかないのは購読リスト・
  既読位置・ピンの 3 つだけ**で、記事本文はフィードから入り直す。この見極めが方針の全て
- **手元（IndexedDB）も同じ規則で間引く。** サーバ側の削除は差分（`sinceId`）に載らず、
  消えたことを伝える手立てが無い。こちらで捨てないと、同期した記事が端末に永久に
  積み上がる（長く使うスマホで効いてくる）。保持期間の日数は `shared/types.ts` に置いて
  両側で共有する。手元だけ長く持っても、サーバに無い記事は次の起動で復元できない
- 間引くのは手元の控えだけで、その起動の間はメモリに残す。`k` で戻れば読めたままにして、
  次の起動で消える形にする
- 狭い画面では左ペインが引き出しの中なので、警告に気付けない。ヘッダ（引き出しの入口）に
  印だけ出す。読む場所には出さない方針は変えない
